# 02 — Backend, Prompts, and Code Generation

## Backend request lifecycle

The FastAPI application is defined in [main.py](../../foxie-backend/app/main.py). Its `ScaffoldRequest` model requires `project_name`, `resource`, `fields_str`, and `api_key`; `database_type` defaults to `sql`, and `enable_auth` defaults to `False`.

`POST /scaffold` checks that an API key was provided, invokes `generate_crud_feature()`, and returns a `GeneratedCode` object. An empty generated file list is returned as an empty result; other exceptions are turned into an HTTP 500 response. `GET /health` is a basic process-health response.

The returned model types are in [models.py](../../foxie-backend/app/core/models.py): `GeneratedCode` holds a list of `CodeFile` values, each containing a relative output path, content, and description.

## Generation pipeline

The generation orchestration lives in [generator.py](../../foxie-backend/app/core/generator.py).

### 1. Resolve the provider key and validate input

- `APIKeyManager.get_api_key()` expects a provided key from the request; backend environment variables are not the key source in the current implementation.
- `parse_fields()` turns strings such as `name:str,price:float` into `Field` records.
- Parsing checks for the `name:type` shape and non-empty pieces. It does not enforce a fixed allowed-type list or Python identifier rules, so input validation can be strengthened.
- The generator accepts `sql` and `mongodb` as database selections and rejects other values.

Field parsing source: [parser.py](../../foxie-backend/app/utils/parser.py). Key handling source: [api_key_manager.py](../../foxie-backend/app/utils/api_key_manager.py).

### 2. Load examples into the prompt

`load_style_guide_snippets()` in [rag.py](../../foxie-backend/app/utils/rag.py) selects example files for the core app plus the requested database type. It can select auth examples too, although the current hybrid auth path calls it with auth examples disabled. The loader removes some comments/whitespace and concatenates the remaining code as prompt context.

This is a simple, file-based form of retrieval-augmented generation: selection is based on configuration, not embeddings or a vector index. A good interview answer should state this distinction clearly.

### 3. Generate core CRUD through Gemini

`_generate_core_crud_files()` builds a prompt specifying the expected application files and their relationships, including config, database session, base/resource models, schemas, CRUD operations, endpoints, router, and main app. It requests JSON matching the `GeneratedCode` schema from the Gemini SDK.

If Gemini returns a recognized 503/unavailable/overloaded error, the function retries up to three attempts with exponential waits of 2 and 4 seconds. Other failures are raised. The retry policy is narrow and can be improved with bounded backoff, jitter, provider-aware error types, and better observability.

The response schema reduces output-shape ambiguity, but it does not prove that the generated source is syntactically valid, imports correctly, or behaves correctly.

### 4. Add authentication from templates when selected

When `enable_auth=True`, the generator:

1. Generates the core CRUD files with auth examples disabled.
2. Renders six database-aware Jinja2 templates under `data/templates/auth/`.
3. Adds the static auth files to the generated bundle.
4. Attempts to add the auth router import and inclusion to generated `router.py`.

This avoids a second LLM generation for the standardized auth files and makes those files more repeatable. The resource-specific code remains model-generated. The current backend route does not accept a `protect_routes` option, so do not claim that resource endpoints are protected by a user-selectable flag in the current implementation.

### 5. Return the file bundle

The backend returns the generated paths and content in the JSON response. It does not write output files; the CLI owns filesystem output.

## Core generation versus other templates

There are two distinct static-generation stages worth separating in an interview:

- **Backend auth templates:** Jinja2 templates in `foxie-backend/data/templates/auth/` are rendered into Python auth files if auth is enabled.
- **CLI output configuration:** `generate_pyproject_toml()` and `generate_env_file()` in [template_generator.py](../../foxie-cli/src/foxie_cli/utils/template_generator.py) create the generated application's dependency manifest and environment defaults. These files are not generated by Gemini.

## Good design discussion points

### Why hybrid generation?

A model is adaptable for arbitrary resource names and fields; templates are predictable for standardized pieces. The split can reduce variability and model usage for auth. The trade-off is that template output may become stale or incompatible with model-generated code unless interfaces and tests enforce compatibility.

### What does structured output guarantee?

It constrains the response shape to a schema-like object. It does not guarantee compilation or runtime correctness. Follow-up validation could parse Python with `ast`, lint/type-check it, import it in an isolated environment, and run generated integration tests before reporting success.

### How would you make generation more reliable?

- Validate resource names and field names/types before calling the provider.
- Use explicit per-database contract tests for the emitted files.
- Run syntax/import checks and tests in an isolated temporary directory.
- Return a structured validation report alongside generated files.
- Add bounded retry/backoff for transient provider errors and avoid retrying permanent errors.
- Track model name, latency, request correlation ID, and failure category, but never log the API key or sensitive prompt data.
- Consider an asynchronous job model for long generations and return a job ID to the CLI.

## Be precise about current capabilities

The repository includes a `CodeValidator` utility in [validators.py](../../foxie-backend/app/utils/validators.py), but its presence alone does not mean the current `/scaffold` request executes validation. The current generator path calls the model and returns the files; the CLI attempts formatting afterward. Describe validation as a future improvement unless you verify a call site has been added.

The codebase also has a `FileGenerator` class, but its module documentation says it is not used in standard mode. The active standard generation path is in `generator.py`.
